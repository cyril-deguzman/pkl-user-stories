User Stories

PKL Boost is a verified-creator add-on inside PKLPlace that lets influencers, court owners, and tournament organizers promote their videos into the PKLLife reels feed. This document captures the user stories grouped by epic, following the classic "As a… I want… so that…" format with acceptance criteria.

PERSONAS

Who we are designing for

🏆
Tournament Organizer
Verified Partner
Runs leagues and tournaments. Wants more registrations and visibility for upcoming events.
Goals Drive event signups · Reach players in target cities · Show ROI on ad spend
🏟️
Court Owner
Verified Partner
Operates one or more pickleball courts. Wants to fill bookings and grow recurring players.
Goals Increase court bookings · Promote clinics · Target by location & skill
⭐
Influencer / Pro Shop
Verified Partner
Sells gear, coaching, or content. Wants reach into the most engaged pickleball audience.
Goals Sell products · Build a following · Boost specific videos

System Design — High-Level Architecture

PKL Boost lives inside the existing PKLPlace FlutterFlow app as an embedded surface. It shares identity and the user base with PKLPlace, ingests video assets from PKLLife, and exposes its own backend services for campaigns, wallet, and ad delivery. Backend persistence is MongoDB, payments through a PH-friendly gateway (GCash + card).

FLOWS

Key end-to-end flows

1. Launch a campaign
Client POSTs /api/campaigns → Gateway auths via PKLPlace JWT → Campaign Service validates targeting + budget, calls Wallet Service to atomically debit (Mongo transaction across wallets + transactions) → creates campaign with status active → fires campaign.created event → Ad Delivery warms its eligibility cache.
2. Serve a sponsored video in PKLLife
PKLLife requests GET /feed-ads?userId=&ctx= → Ad Delivery looks up eligible campaigns (Redis-cached eligibility set), filters by audience + frequency cap, ranks by pacing target, returns 0 or 1 ad reference. PKLLife renders the video; client posts an impression (and later view/click) event back to the API. Events go through the queue into Metrics Pipeline.
3. Roll up spend
Every 5 min, the rollup worker reads new events, dedupes via dedupeKey, upserts into campaign_metrics for the day, and emits a spend.delta message → Wallet Service debits the partner wallet for the corresponding cost (CPV table). If the campaign hits its daily cap or wallet runs dry, status flips to paused.
4. Top up wallet
Client triggers a top-up → Wallet Service creates a pending transaction and a payment intent at the gateway → gateway returns redirect / SDK params → user completes payment → gateway webhook hits the API → wallet credited, transaction marked succeeded, receipt PDF queued, partner notified.
NFRs

Non-functional considerations

Performance
Dashboard p95 < 800ms. /feed-ads p95 < 120ms (Redis-cached eligibility, single Mongo lookup max).
Consistency
Wallet operations use Mongo multi-doc transactions across wallets + transactions. Spend rollups are eventually consistent with at-most-1-min lag visible to partners.
Security
JWT from PKLPlace at the gateway. Card data never touches our servers — gateway-tokenized. KYC docs encrypted at rest in S3.
Auditability
Append-only transactions ledger. Campaign edits logged with actorId + diff. Admin actions emit audit events.
Scale targets (yr 1)
~5K verified partners, ~50K active campaigns/yr, ~2M ad impressions/day. Built to grow 10× with horizontal Node + Mongo sharding by partnerId.
Observability
Structured logs (pino) → centralized log store. Metrics via Prometheus on every service. Per-campaign delivery dashboards for ops.
Open questions for the backend dev: (1) Will Boost share a single Mongo cluster with PKLPlace/PKLLife, or run its own? (2) Is there an internal event bus we should reuse for cross-service messaging, or do we stand up our own (Kafka / Redis Streams / BullMQ)? (3) Confirm the chosen PH payment aggregator (PayMongo vs Xendit) so we can finalize the top-up flow.
